# FairVote — 1. Модель угроз

Статус: проектное решение, код не написан. Версия 1.0.

Область: неофициальная платформа онлайн-голосования «FairVote». Не является системой
ГАС «Выборы», не имеет юридической силы, не заменяет установленную законом процедуру
голосования. Это техническая песочница проверяемости.

---

## 1.1. Активы

| ID | Актив | Почему ценен | Где живёт |
|----|-------|--------------|-----------|
| A1 | Тайна голоса (связь «человек → выбор») | Политические взгляды — особая категория ПДн; разглашение необратимо | ballot_box (шифртекст) + registry (факт участия) |
| A2 | Реестр избирателей (кто допущен) | Список участников политического события — сам по себе чувствителен | registry |
| A3 | Учётные данные (пароль, TOTP, recovery) | Захват аккаунта → голосование от имени человека | registry |
| A4 | Документы-доказательства | Сканы с ПДн (ФИО, адрес, серия/номер) | var/proofs (шифртекст), удаляются после решения |
| A5 | Целостность журнала | Без неё непроверяемо ничего | audit_log |
| A6 | Приватный ключ опроса | Его компрометация до закрытия = чтение всех голосов | офлайн, вне сервера |
| A7 | Ключи сервера (pepper, linkage, master) | Pepper → офлайн-перебор PII; linkage → деанонимизация | env/файл вне web-root |
| A8 | Доверие к выдаваемому JS | Подмена JS = подмена шифрования/выбора | static/ + хэши в журнале |

## 1.2. Акторы

| ID | Актор | Возможности | Мотивация |
|----|-------|-------------|-----------|
| P1 | Анонимный интернет | Всё, что доступно без аутентификации; брутфорс, сканирование, накрутка | срыв, накрутка, deface |
| P2 | Зарегистрированный избиратель | Свой аккаунт, свой голос, свой секрет, свой браузер | переголосовать, «доказать» свой голос, накрутить |
| P3 | Недобросовестный админ | Создание/правка опросов до старта, публикация ключа, доступ к серверу как к приложению | сдвинуть расписание, подменить кандидатов, «утечь» данные |
| P4 | Взломщик БД/бэкапа | Дамп registry.sqlite или бэкапа, без кода и ключей env | деанонимизация, продажа списков |
| P5 | Хостинг-провайдер (PA) и его сотрудники | Root на VM, access-логи, снапшоты диска, сетевой перехват | любопытство, принуждение |
| P6 | Принуждающий (coercer) | Физический доступ к избирателю, требует голос, требует «доказательство» | покупка голосов, давление |
| P7 | Оператор платформы (владелец кода) | Может менять код и деплой | «поправить» результат |
| P8 | Государственный/сетевой противник | Блокировки, MITM при отсутствии TLS | цензура, слежка |

## 1.3. Границы доверия

```
[браузер избирателя] --TLS--> [uWSGI/Flask на PA]
      |                            |
      |                             +-- registry.sqlite      (PII-минимум, ключи env)
      |                             +-- polls.sqlite         (публичный контент)
      |                             +-- ballot_box.sqlite    (шифртексты, без user_id)
      |                             +-- audit_log.sqlite     (append-only цепочка)
      |                             +-- var/proofs/          (шифртекст, короткий TTL)
      |
      +-- офлайн: приватный ключ опроса (генерён до старта, вне сервера)

[публичный верификатор: verify.py / чужой скрипт] <-- JSONL-экспорт, ключ, корень
[внешние свидетели: зеркала, публикации хэша] <-- контрольные точки журнала
```

Доверяем: TLS-терминации PA, честности libsodium/OpenSSL/Argon2, системным часам
(до степени, оговорённой ниже), тому, что избиратель сохранил свой секрет.

Не доверяем: браузеру (XSS, расширения), сети, БД на диске, бэкапам, админу,
оператору, хостингу, часам настолько, чтобы строить на них тайну голоса.

## 1.4. Ключевой принцип

Тайна голоса в MVP обеспечивается **разделением хранилищ и процессом**, а не
криптографией. После решения D-2 (docs/05) связи «человек ↔ ballot_id» в схеме нет
вообще: реестр знает только факт участия (`participation`), ящик — только `ballot_id`
и шифртекст. Плата за это — отказ от переголосования (см. T7). Криптографическая
несвязываемость от оператора (слепые подписи, RFC 9474) — этап 2. Всё, что ниже, читать
с этой оговоркой: сильнее всего оставшиеся риски — метаданные хостинга (T10) и
неизменяемость принуждённого голоса (T7).

## 1.5. Таблица угроз

Формат: ID · угроза · сценарий · меры · остаточный риск.

### A. Утечка БД и бэкапов

**T1. Дамп registry.sqlite целиком.**
Сценарий: SQL-инъекция/SQLi-подобная ошибка, украденный файл, снапшот диска.
Меры: в registry нет ФИО/паспорта/адреса/email — только `login`, Argon2id-хэш пароля,
`voter_key` (необратимый), округ, статус. TOTP-секрет — AES-256-GCM. IP не хранится
(только HMAC(IP) в счётчиках с TTL ≤ 24 ч). Пароли: Argon2id m=46 MiB, t=1, p=1.
Остаточный риск: `login` может быть псевдонимом-ФИО (выбор пользователя), `voter_key`
детерминирован от PII и при утечке **pepper** даёт офлайн-проверку «есть ли этот
человек в реестре» (см. T1a). Смягчение: предупреждение при регистрации, pepper вне БД.

**T1a. Pepper + офлайн-перебор PII по voter_key.**
Сценарий: утёк дамп БД и env (или бэкап env). Атакующий, зная ФИО+ДР+паспорт,
вычисляет voter_key и проверяет членство; перебор серии/номера — 10^9..10^10
вариантов при Argon2id 64 MiB ≈ сотни GPU-лет, но членство конкретного человека
проверяется за одно вычисление.
Меры: это **неустранимое свойство** требования «один человек — один аккаунт без IdP».
Частично: (а) реестр удаляет `voter_key` через N дней после закрытия; (б) в публичную
Меркл-структуру попадает `SHA-256("fairvote/elig/v1" || voter_key)` и только корни,
листья не публикуются (T15); (в) pepper хранится отдельно от БД и от бэкапа БД;
(г) ротация pepper невозможна без потери свойства «один человек — один аккаунт» —
задокументировано. Остаточный риск: высокий по последствиям, низкий по вероятности;
при утечке реестр надо считать раскрытым и уведомить пользователей.

**T1b. Утечка бэкапа ballot_box/audit_log.**
Меры: там нет PII — шифртексты, слоты (час), хэши. Публикуются и так (после закрытия).
Остаточный риск: метаданные тайминга (T6).

**T1c. Утечка приватного ключа опроса до закрытия.**
Меры: ключ генерируется офлайн CLI-скриптом, на сервер не попадает; сервер знает только
публичный ключ. Компрометация сервера не даёт чтения голосов. Остаточный риск: кража
у админа на его машине — вне модели (T23).

### B. Недобросовестный админ

**T2. Правка опроса после старта / подмена кандидатов.**
Меры: DB-триггер `poll_immutable_after_start` (RAISE ABORT) + прикладная проверка +
`poll_revision` с хэшем снапшота + запись `poll.start` в цепочке. Любая правка после
старта — это либо ошибка БД (abort), либо расхождение с опубликованным хэшем, видимое
любому. Остаточный риск: админ с root на файле может обойти триггер — тогда расхождение
цепочки/хэша обнаруживается (T4, T13).

**T3. Админ читает реестр или промежуточные результаты.**
Меры: админские хэндлеры физически не получают движок registry (DI: admin blueprint
зависит только от polls-сервиса). Промежуточные результаты он читать не может не
политически, а **криптографически**: приватного ключа на сервере нет до публикации.
Турновер-агрегаты публичны. Тест: `test_admin_has_no_registry_access`.
Остаточный риск: админ — он же оператор с root (T13) читает файлы напрямую; против
этого — только шифрование (T4) и внешняя проверяемость.

**T4. Ретроактивная правка журнала (в т.ч. админом).**
Меры: цепочка хэшей; триггеры `entry_no_update`/`entry_no_delete`; ежедневная подпись
Ed25519 головы (checkpoint); публикация головы во внешнем канале; экспорт JSONL.
Остаточный риск: пересборка всей цепочки с другим содержимым даёт валидную цепочку —
обнаруживается только по внешней копии головы/подписи (T14).

**T5. Админ «сливает» список участников.**
Меры: у него нет доступа к registry; экспорт реестра не предусмотрен вообще (нет
эндпоинта, нет CLI-команды дампа реестра в открытом виде). Бэкап реестра —
зашифрованный, ключ вне платформы.

**T5a. Админ меняет расписание «в свою пользу».**
Меры: смена расписания возможна только до старта, каждая — запись в публичном журнале
с diff; после старта — только сокращение? Нет: после старта ничего. Досрочное закрытие
запрещено, закрытие возможно только после `ends_at` (проверка серверного времени +
публикация времени закрытия в журнале).

### C. Принуждение избирателя

**T6. Привязка «человек → слот времени».**
Сценарий: в маленьком округе один голос в час; сопоставление `participation.voted_on`
(дата) с `ballot.slot` (час) сужает круг.
Меры: `participation` хранит только дату; `ballot.slot` — час; голоса пишутся пачками
через очередь со случайной задержкой и перемешиванием, поэтому порядок `seq` не равен
порядку прихода; порог k скрывает результаты малых округов; при k>числа голосов
округ публикуется как «<k». Остаточный риск: **остаётся** — при 3 голосующих в округе
и трёхчасовом окне корреляция вероятна. Полное устранение требует cover traffic или
анонимной сети (этап 3).

**T7. Принуждение «проголосуй за X, покажи подтверждение».**
Сценарий: coercer требует секрет/ballot_id и проверяет.
Меры: (а) бюллетени публикуются **только после закрытия** — во время голосования
проверить «мой голос уже в ящике» нельзя; (б) предупреждение о принуждении перед
отправкой и отдельный экран подтверждения необратимости; (в) UI предлагает голосовать
в приватном окне/с чужого устройства; (г) опция отложенной публикации ключа
(`key_publish_after`, docs/05 D-4), чтобы проверка не была доступна сразу после закрытия.
Остаточный риск: **критический**. Решением D-2 переголосование отменено (ради полного
отсутствия связи «человек ↔ ballot_id»), поэтому принуждённый голос неизменяем, а
coercer, получивший секрет, после публикации ключа расшифрует голос. Схема
«опубликовать ключ и расшифровать всем» несовместима с receipt-freeness. См. §1.6 N4.

**T8. Покупка голосов с проверкой.**
Меры: публикация ящика и ключа только после закрытия лишает покупателя возможности
проверить голос *в процессе*; опция отложенной публикации ключа; k-порог. После
публикации ключа проверка «проданного» голоса становится возможной — переголосования
нет, поэтому «отменить проданный голос» нельзя. Полностью не решается (T7).

**T9. Избиратель «доказывает» свой голос добровольно.**
Меры: никаких «квитанций с выбором»; бюллетень отдаёт только `ballot_id`, не выбор.
Остаточный риск: после публикации ключа любой с `ballot_id` читает выбор.

### D. Деанонимизация по метаданным

**T10. IP-адреса в логах хостинга.**
Сценарий: access-логи PA содержат IP + путь + время; их нельзя отключить.
Меры: (а) в URL нет ни секретов, ни ballot_id, ни логина — все чувствительные
действия POST-ом, ответы без кэша; (б) голосование — POST на общий путь; (в) в наших
логах нет IP (только HMAC-счётчики, TTL ≤ 24 ч); (г) предупреждение на странице
«Как устроено»: хостинг видит IP и время; рекомендовано использовать Tor/VPN, если
это важно; (д) при переходе на собственный хостинг — access-log off.
Остаточный риск: **высокий и неустранимый на PA** — провайдер может сопоставить
«кто, когда, какой poll_id» (но не выбор).

**T11. Порядок записей / автоинкремент.**
Меры: пачечная запись, случайный порядок внутри пачки, случайная задержка 0..N минут,
`slot` — час; `ballot.seq` не коррелирует с временем прихода; никакого `user_id`/IP/
session в ящике (тест на схему). Остаточный риск: размер пачки = число голосов за
интервал; при малом k это уже скрыто порогом.

**T12. Метаданные размера.**
Меры: plaintext бюллетеня дополняется до **фиксированного** размера опроса
(`ballot_plaintext_bytes`, по умолчанию 1024), поэтому все шифртексты опроса имеют
одинаковую длину; случайный padding внутри. Остаточный риск: нет (кроме размера,
общего для всех).

**T12a. Признак «переголосовал» через число строк.**
Меры: несколько строк с одним ballot_id — норма, счёт идёт по последней; публикуется
только итоговое правило и список superseded.

### E. Накрутка и фиктивные избиратели

**T13. Сибил-аккаунты (много аккаунтов одного человека).**
Меры: `voter_key` = Argon2id(нормализованные ФИО+ДР+документ, salt=pepper), UNIQUE;
регистрация невозможна без прохождения провайдера верификации; в проде DemoProvider
запрещён (fail-closed при `DEMO_MODE=false`). Остаточный риск: целиком определяется
качеством провайдера; никакая автоматическая проверка скана паспорта не является
достоверной (мы её и не имитируем). Честная оценка: против организованной накрутки
без внешнего IdP платформа беззащитна.

**T13a. Подбор voter_key «в лоб» (регистрация на выдуманного человека).**
Меры: провайдер верификации (документ проверяется человеком/IdP), rate limit,
`voter_key` не возвращается клиенту. Остаточный риск: DemoProvider в демо-режиме
позволяет всё — это явно объявлено баннером.

**T13b. Двойная регистрация из-за нормализации (легитимный человек).**
Сценарий: «Иванов» и «ИВАНОВ» с разным написанием дают разные voter_key → два аккаунта.
Меры: предпросмотр нормализованной строки и явное подтверждение; UNIQUE-индекс;
ручное разбирательство через провайдера (не админа FairVote).
Остаточный риск: средний; это цена детерминированной схемы (см. §1.6).

**T14. Пустые/мусорные бюллетени для раздувания.**
Меры: rate limit на голос, один бюллетень на (poll, user), проверка структуры sealed box,
публичный подсчёт «недействительных» при расшифровке. Остаточный риск: мусор в своём
округе виден публично; на итог не влияет.

**T15. Меркл-листья как оракул членства.**
Сценарий: публикация листьев `H(voter_key)` + знание PII человека → проверка «он в
списке». Меры: публикуются **только** корни (агрегатный и по округам) и счётчики;
листья и пути Меркла не публикуются; персональный путь включения выдаётся только
владельцу аккаунта после старта (за аутентификацией, rate-limited).
Остаточный риск: нельзя независимо пересчитать корень по листьям (приходится доверять
серверу в части *состава* списка) — это осознанный размен, зафиксирован в §1.6.

### F. XSS, CSRF, брутфорс, инъекции

**T16. XSS через админский контент (описание, биографии).**
Меры: Markdown → HTML на сервере, nh3 с белым списком (без `style`, `class` кроме
разрешённых, `href` только http/https/mailto, `rel="noopener nofollow ugc"`), строгая CSP
`script-src 'self'` без `unsafe-inline`, шаблоны Jinja2 с автоэскейпом.
Остаточный риск: low.

**T16a. XSS через пользовательский ввод (логин, кодовое слово, ссылка).**
Меры: экранирование везде, `link_url` валидируется схемой, никакого `|safe` вне
санитизированного HTML.

**T17. CSP-совместимость (нет inline).**
Меры: все стили в CSS-файлах, JS — во внешних модулях с nonce не нужен; `style-src 'self'`
(без `unsafe-inline`), `script-src 'self'`, `base-uri 'none'`, `form-action 'self'`,
`frame-ancestors 'none'`. Тест: заголовки на всех маршрутах, включая ошибки.

**T18. CSRF.**
Меры: токен в серверной сессии (не в cookie), проверка на всех небезопасных методах,
`Origin`/`Sec-Fetch-Site` как второй барьер, SameSite=Strict, никаких GET-мутаций.
Остаточный риск: low.

**T19. Брутфорс пароля/TOTP, user enumeration.**
Меры: Argon2id; лимиты в БД (аккаунт+IP, Flask-Limiter с собственным SQLite-хранилищем —
у `limits` нет SQLite-бэкенда, см. docs/02 §2.9); lockout аккаунта с экспоненциальной
задержкой; одинаковые тексты ошибок; проверка пароля выполняется и для несуществующего
логина (dummy-hash) — выравнивание времени; TOTP с защитой от replay (`totp_last_step`)
и лимитом попыток; recovery-коды Argon2id, одноразовые.
Остаточный риск: distributed brute-force по IP-пулу — только lockout по аккаунту.

**T20. SQL-инъекции.**
Меры: SQLAlchemy Core/ORM с параметризацией, никакой конкатенации; DDL — в отдельных
.sql-файлах без пользовательских данных. Остаточный риск: low.

**T21. Session fixation / кража cookie.**
Меры: серверные сессии (в БД, cookie только ID), ротация ID при логине и смене уровня,
TTL 20 мин idle / 8 ч абсолют, `Secure/HttpOnly/SameSite=Strict`, в БД хранится
`SHA-256(token)`, отзыв всех сессий при смене пароля.

**T22. Загрузка документов (malicious file).**
Решением D-3 файлы **не принимаются**: нет парсера недоверенных форматов, нет хранения
сканов, нет EXIF-проблем. Документ передаётся провайдеру верификации по его каналу вне
платформы; в FairVote попадают одноразовый код (только SHA-256), метод и решение.
Остаточный риск: у провайдера остаются свои ПДн — это вне периметра FairVote.

**T23. Компрометация машины админа / приватного ключа.**
Меры: вне модели приложения; организационные (офлайн-машина, разделение ключа по Шамиру,
разные люди). Документировано.

### G. Честность подсчёта

**T24. Сервер добавляет/выбрасывает бюллетени.**
Меры: ящик публикуется целиком после закрытия; счёт считается публично `verify.py`;
счётчики проголосовавших по округам публикуются и сверяются с расшифрованными
бюллетенями; каждая пачка коммитится в журнал корнем Меркла; избиратель может проверить
присутствие `ballot_id`. Остаточный риск: **остаётся** — сервер может не записать
пришедший бюллетень (избиратель увидит отсутствие по ballot_id → скандал, но не
восстановление голоса). Против «добавил левый бюллетень» защита слабая: нужен
подписанный избирателем бюллетень/слепые токены (этап 2).

**T25. Подмена публикуемого приватного ключа при закрытии.**
Меры: commitment — `key_fingerprint` публикуется в журнале **до старта**; при закрытии
публикуется ключ, хэш которого должен совпасть с commitment; расхождение = публичный
инцидент. Остаточный риск: админ сгенерировал ключ, но потерял — выборы нельзя
расшифровать (fail-safe: результаты не публикуются, объявляется инцидент).

**T26. Подмена JS.** См. §1.6, T27.

## 1.6. От чего НЕ защищаемся (и чем смягчаем)

| # | Не защищаемся | Почему невозможно/дорого | Смягчение |
|---|---------------|--------------------------|-----------|
| N1 | **Оператор/сервер подменяет JS** (собирает `choice` в открытом виде, шифрует своим ключом) | Клиент — это код, который отдаёт сервер; без доверенного клиента TLS-модель рушится | Хэши JS публикуются в append-only журнале до старта; воспроизводимая сборка; офлайн-сборка и сравнение; сторонние наблюдатели; офлайн-`verify.py`. Это **обнаружение**, не предотвращение. Без доверенного клиента (расширение, отдельный бинарник) гарантий нет |
| N2 | Оператор **добавляет** бюллетени | Нет подписи избирателя на бюллетене в MVP | Публичный ящик, сверка счётчиков, независимый пересчёт, внешние зеркала; этап 2 — слепые подписи + публичные nullifier'ы |
| N3 | Оператор **удаляет** бюллетень | Сервер — точка записи | Избиратель проверяет свой `ballot_id` в опубликованном ящике; расхождение публично; восстановление невозможно |
| N4 | Принуждение после публикации ключа | Схема «опубликуй ключ, расшифруй всем» = отсутствие receipt-freeness; после D-2 переголосования нет, значит голос неизменяем | Отложенная публикация ключа (`key_publish_after`), k-порог, предупреждения, приватное устройство. Полного решения в MVP нет |

| N7 | Глобальный сетевой противник / блокировки | Вне модели | TLS + HSTS; зеркала; `.onion` невозможен на PA |

## 1.7. Не-технические требования (обязательны для честности модели)

1. Публичное описание того, кто владеет сервером и кто генерирует ключ опроса.
2. Публикация головы журнала в независимом канале (не на нашем домене) — ежедневно/еженедельно.
3. Минимум два независимых зеркала JSONL-экспорта.
4. Ротация администраторов, отсутствие «суперпользователя» с правом правки журнала.
5. Уведомление пользователей в случае инцидента (шаблон в docs/04).
6. Юридическая проверка: политические взгляды — особая категория ПДн (152-ФЗ), нужно
   согласие и законное основание; в демо-режиме — только синтетические данные.
