# Проверка FairVote — 26 октября 2026

Проверен исходный коммит `6316dce837a52340d7980c037328e0253af7c74c`.
Изменения этой ветки исправляют ряд ошибок, но не делают проект готовым для
реального политического голосования в условиях репрессий. Проверялись исходники,
тесты и локальные сценарии; конфигурация действующего хостинга и реальные журналы
провайдера не проверялись. Веб-приложение не развёртывалось.

## Что уже реализовано

Это функциональный прототип: регистрация, Argon2id, TOTP, серверные сессии, CSRF,
лимиты в SQLite, заморозка опроса, шифрование в браузере, очередь, журнал, экспорт
и отдельный пересчёт существуют в коде. Исходный набор дал **514 прошедших тестов**;
заявление README о 524 тестах не соответствовало этому запуску. Число тестов не
служит доказательством безопасности криптографического протокола.

Для заявленной задачи нужно отдельно обеспечить: допустимость участника,
единственность голоса, невозможность связать личность с выбором, неизменность
принятого бюллетеня и проверяемость подсчёта. Хэширование само по себе не решает
все эти задачи. Хэш выбора из нескольких кандидатов легко проверить перебором;
текущие бюллетени поэтому **шифруются**, а не просто хэшируются.

## Блокирующие ограничения протокола, которые остаются

### 1. Публичный ключ расшифрования раскрывает все бюллетени

`polls/lifecycle.py:publish_private_key` сохраняет приватный ключ;
`web/transparency.py:published_key` отдаёт его всем. Публичный ящик содержит
`ballot_id`, округ, час и шифртекст. После публикации ключа **любой читатель**
расшифровывает каждый бюллетень без секрета участника. Секрет нужен, чтобы найти
конкретную строку, а не чтобы расшифровать её.

Поэтому порог `k` скрывает только детализацию на странице: выгрузка позволяет
пересчитать даже округ с единственным участником. Публикация с задержкой лишь
откладывает раскрытие. Получив связь аккаунт → `ballot_id`, противник позднее
узнает выбор. Связь может появиться из наблюдения запроса, принуждения или данных
устройства. Переголосования и защиты от предъявления подтверждения выбора нет.

Следующий этап — выбрать и независимо проверить протокол с публикацией
доказательств корректного подсчёта без раскрытия всех индивидуальных бюллетеней.
Пороговое расшифрование несколькими держателями ключей само по себе не помогает,
если затем публикуются открытые индивидуальные голоса.

### 2. Сервер видит участника и его бюллетень одновременно

`web/vote.py:submit` получает авторизованную сессию и тело с `ballot_id` и
шифртекстом. Один процесс имеет ключи и доступ ко всем четырём БД.
Отсутствие `user_id` в таблице `ballot` полезно для минимизации данных, но не
защищает от наблюдающего оператора, скомпрометированного приложения или хостинга.
Точные времена сессий, регистрации, входов и очереди дают дополнительные
возможности корреляции. Корреляция может быть возможна и без прямой ссылки в схеме.

Нужны разделение выдачи допуска и подачи голоса, анонимные одноразовые полномочия,
отдельные границы доверия и анализ сетевых метаданных. Подмена JS сервером остаётся
возможна: манифест, полученный с того же сервера, без независимого доверенного
источника не предотвращает адресную подмену одному участнику.

### 3. Нет публичного доказательства «допущенный человек → один голос»

Корень Меркла списка допущенных не доказывает, что каждый принятый шифртекст
разрешён ровно одному человеку из этого списка. Администратор сервера может
дописать бюллетени и пересчитать журнал; публичный ключ шифрования доступен всем.
Обычные SQL-ограничения работают против ошибок приложения, но не владельца БД.

Нужны независимо проверяемые анонимные полномочия и защита от их повторного
использования. Слепые подписи могут быть частью протокола, но не решают все
проблемы автоматически. Независимые наблюдатели должны сохранять подписанные
контрольные точки и сверять истории между собой. Подпись ключом, который оператор
может заменить вместе с журналом, не является внешним якорем доверия.

### 4. Ручная верификация не связывает проверенный документ с зарегистрированными данными

`ManualProvider` выдаёт код; `verification.decide` меняет статус найденного по коду
аккаунта. В решение не передаются проверенные поля личности и округа, и там нет
сравнения с `voter_key` регистрации. Оператор может подтвердить документ одного
человека для аккаунта с другими заявленными данными.

Кроме того, уникальность ключа — это уникальность нормализованной комбинации
ФИО/даты/типа/номера документа, а не человека: другой документ может дать другой
ключ. Реальный IdP/электронная подпись не интегрированы; предусмотрены интерфейс,
ручное решение через CLI и демонстрационное подтверждение. Справочник округов —
синтетический пример РФ, не готовая база для РФ/Беларуси.

До запуска нужны проверенный порядок идентификации/дедупликации, привязка
подтверждения к зарегистрированной личности и округу, модель доступа сотрудников
провайдера и порядок обработки исходных данных. Самописную «проверку паспорта»
по распознанному скану нельзя считать достаточной.

### 5. Несколько БД не образуют одну атомарную операцию

`ballots/service.py:accept_ballot` сначала сохраняет очередь, затем участие,
затем подтверждение в отдельных транзакциях. Сбой после записи участия оставляет
участника без возможности голосовать, а его бюллетень — вне подсчёта. В текущей
схеме нет связи, позволяющей безопасно восстановить этот голос автоматически.
Новая ветка прекращает ложный успешный ответ и сохраняет следы сбоя, но не
устраняет само окно сбоя. Повтор после выгрузки из очереди тоже не имеет полной
долговременной идемпотентности.

`ballots/queue.py:commit_batch` коммитит журнал до коммита ящика. При сбое остаётся
запись батча без самого батча. Аналогичные последовательности есть при изменении
жизненного цикла. Порядок блокировок предотвращает некоторые взаимные блокировки,
но не превращает независимые коммиты в атомарную транзакцию.

Нужны журнал восстанавливаемых операций/протокол сверки и испытания с остановкой
процесса на каждом шаге, согласованные с требованиями анонимности. Не следует
добавлять постоянную таблицу «аккаунт → бюллетень» только ради удобства восстановления.

### 6. Независимый проверяющий всё ещё проверяет не все обязательства

Исправленная сверка ловит описанный опыт с лишним голосом, если передан журнал.
Но лист батча v1 коммитит **шифртекст**, не весь публичный конверт: `ballot_id`
не связан этим корнем. Без отдельно доверенной подписи выгрузки замена идентификатора
может нарушить поиск своего бюллетеня, не изменив корень батча.

Также `poll.json` не содержит полного снимка, из которого построен `content_hash`
старта: проверка названий/вариантов/порядка конкурсов против замороженного
содержимого не завершена. Перед реальным запуском нужен версионированный формат
обязательства по полному конверту, воспроизводимый снимок опроса и строгая
валидация всех входных схем с одинаковыми правилами на сервере и в проверяющем.

## Данные и эксплуатация

- Исходные ФИО и данные документа поступают на сервер при регистрации. Они не
  сохраняются в таблицах, но доступны серверному процессу при обработке запроса.
  `voter_key` с секретным pepper уменьшает риск утечки; утечка pepper и реестра
  позволяет проверять известные личности. Это псевдонимизация, а не абсолютная
  анонимность. Логин, округ, факт участия и временные метки сохраняются открыто.
- `purge_retention` ориентируется на участвовавших пользователей и удаляет только
  `voter_key`: неучаствовавшие аккаунты и `auth_event` не получают полного срока
  очистки. Нужна политика для каждой категории, включая очереди, резервные копии
  и журналы хостинга. Сохранение неподтверждённых строк ради расследования теперь
  явно требует отдельного контролируемого срока хранения.
- `backup_registry` сначала пишет незашифрованную временную SQLite-копию на диск,
  затем читает, удаляет и шифрует. Сбой до удаления оставляет открытый файл;
  удаление не гарантирует стирание носителя. Желательна копия в памяти с шифрованием
  до записи и ограниченными правами на выходные файлы.
- Шифрованный бэкап только реестра не заменяет согласованное восстановление
  опросов, ящика и журнала. После потери этих БД одних экспортов недостаточно,
  чтобы просто восстановить прежний рабочий экземпляр. Нужен проверенный план
  восстановления всех хранилищ, ключей и независимых контрольных точек.
- Удалённые тестовые БД и demo-key остаются в старом коммите. Проверено их
  происхождение как демонстрационных артефактов по путям и содержимому сценария;
  это не доказывает отсутствие их повторного использования на хостинге. Если
  опубликованный ключ использовался вне демо, считайте его раскрытым.
- В исходном репозитории отсутствуют workflow CI и отдельный файл лицензии.
  Проверки браузера ограничивались отдельными функциями, а не нажатием кнопки.
  Добавленный Node-сценарий покрывает регрессию обработчика, но не заменяет
  полноценный браузерный сценарий и тестирование производственного окружения.
- Даже исправная система измеряет голоса добровольно пришедших участников.
  Без представительной выборки и проверки охвата её результат нельзя выдавать
  за доказанный результат голосования всего населения или официальных выборов.

## Приложенный патч и порядок применения

Патч корректно применялся к исходному коммиту через `git apply --check` и уже
включён в эту ветку. Он исправляет реальный дефект лимитов на PythonAnywhere.
Официальная документация: <https://help.pythonanywhere.com/pages/WebAppClientIPAddresses/>.

Предпочтительный путь — принять pull request целиком. Повторно применять patch
после этого не нужно. Для отдельного применения к исходной версии:

```bash
git switch -c fix/pythonanywhere-client-ip
git apply --check /path/to/0001-fix-client-ip-behind-pythonanywhere.patch
git apply /path/to/0001-fix-client-ip-behind-pythonanywhere.patch
python -m pytest tests/test_client_ip.py tests/test_ratelimit.py tests/test_config.py
```

Для PA добавьте до `create_app()` в WSGI-конфигурации или её окружении:

```python
os.environ["FV_TRUST_X_REAL_IP"] = "1"
```

Затем Reload web app. На другом хостинге по умолчанию оставьте `0`: произвольное
доверие входному заголовку позволяет обходить лимиты подменой IP. Этот флаг
исправляет определение адреса для лимита, но не анонимность и не логи провайдера.

## Приоритет следующего этапа

1. Зафиксировать модель противника и честные гарантии: считается ли оператор
   потенциально злонамеренным, допускается ли раскрытие отдельных голосов.
2. Выбрать протокол допуска, анонимной подачи и проверяемого агрегированного
   подсчёта; согласовать его с независимыми специалистами до сбора реальных данных.
3. Закрыть окна сбоев, привязку верификации, полноту обязательств и восстановление.
4. Проверить реальные настройки хостинга, доступ сотрудников, обработку исходных
   данных, сроки удаления и устойчивость при нагрузке; запустить CI и сценарии
   в настоящем браузере.

До выполнения этих пунктов разумный режим использования — демонстрации и
эксперименты с вымышленными личностями и голосами.
