## Что входит в модуль

| Файл | Роль |
|------|------|
| `fairvote/audit/models.py` | SQLAlchemy Core-таблицы `entry`, `checkpoint` (зеркало DDL) |

| `flask audit-head / audit-pubkey / checkpoint / verify-chain / export-audit` | эксплуатация |

## Обоснования

### 1. В record входит ровно пять полей

`seq, ts, kind, poll, payload` — и ничего вне хэша. Любое «полезное» поле рядом с
record, не покрытое хэшем, стало бы каналом для незаметных пометок (например, отметки
«этот бюллетень от такого-то»). Поэтому `verify.py` отдельно ругается на `EXTRA_FIELD`:
даже безопасное на вид дополнение видно проверяющему.

### 2. Подпись контрольной точки покрывает JSON, а не бинарный хэш

`{"hash": "...", "seq": N, "v": 1}` — самодостаточно: сторонний проверяющий не должен
знать двоичную раскладку, чтобы проверить подпись. `seq` внутри сообщения закрывает
перенос старой подписи на укороченную цепочку (отрезали хвост — подпись не подойдёт).

### 3. Конфликт контрольной точки — это отказ, а не «обновление»

Если `seq` уже отмечен другим хэшем, `create_checkpoint` падает. Это не nuisance:
такое состояние означает перезапись истории, и молча «переподписать» его было бы
худшим из возможных решений.

### 4. `BEGIN IMMEDIATE` вокруг чтения головы и вставки

Два воркера, читающих голову одновременно, иначе создали бы две записи с одним
`prev_hash` — цепочка разветвилась бы, а проверка показала бы `CHAIN_BREAK` на
здоровой системе. Тест `test_concurrent_appends_serialise` (4 потока × 10 записей)
фиксирует это поведение; добавлен и ограниченный ретрай на `BEGIN IMMEDIATE`
(`database is locked`), но **не** на тело транзакции — повтор тела мог бы применить
побочные эффекты дважды.

### 5. Проверяющий не переиспользует наш код

`verify.py` содержит собственную копию канонического JSON. Это считается дублированием
осознанно: если бы он импортировал `fairvote`, аудитор доверял бы тому же коду, который
проверяет. Обе реализации закреплены общими векторами и тестом на совпадение байтов
(`test_canonical_implementations_agree`), а также тестом на одинаковый результат
хэширования одного и того же record.

### 6. Что именно ловит `verify_rows`

| Код | Что случилось |
|-----|---------------|
| `HASH_MISMATCH` | поле записи изменено |
| `CHAIN_BREAK` | `prev_hash` не совпадает с предыдущей записью (вставка/удаление) |
| `SEQ_GAP` | пропущен номер — запись удалена |
| `EXTRA_FIELD` | добавлено поле вне хэша |
| `MISSING_FIELD` | запись обрезана |
| `MALFORMED_ROW` | не hex / не та длина / не объект |
| `NON_CANONICAL` | payload нельзя канонизировать (float, не-строковый ключ) |
| `BAD_TIMESTAMP` | время не в формате UTC `…Z` |
| `UNKNOWN_KIND` | вид записи вне опубликованного словаря |
| `SIG_INVALID` / `PUBKEY_MISMATCH` | подпись не сходится с независимо полученным ключом |

Отдельно: изменённая запись **не** даёт `CHAIN_BREAK` — ссылка остаётся прежней.
Это и есть причина, по которой проверяющий обязан пересчитывать хэш каждой записи, а
не только сверять ссылки (тест `test_verify_rows_detects_edited_record`).

## Какие угрозы закрывает

* **T4** (ретроактивная правка журнала): цепочка + триггеры + контрольные точки.
* **T24** (подмена опубликованного): `verify.py` пересчитывает всё по файлу.
* **T25**, частично: commitment ключа будет коммититься в эту же цепочку (M3).
* **T14** (повторный запуск операций): `has_entry` даёт идемпотентность `poll.start`.

## Остаточные риски

* Оператор может **пересобрать** цепочку целиком с другим содержимым: локальная
  проверка это не поймает. Ловится только сравнением с ранее опубликованной головой
  (внешний канал), поэтому `checkpoint --note` и ручная публикация — обязательная часть
  процесса, а не «приятная опция».
* `verify.py` проверяет только цепочку. Расшифровка бюллетеней и сверка итогов — M6/M10.
