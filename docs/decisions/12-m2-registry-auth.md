## Обоснования

### 1. Нормализация — часть криптосхемы, а не «косметика»

`voter_key` детерминирован, поэтому «Иванов» и «ИВАНОВ» с разным написанием дали бы
две записи. Нормализация: NFKC → casefold → `ё→е` → удаление пунктуации → сжатие
пробелов; для документа — только `[0-9A-Z]` с заменой кириллических гомоглифов
(`АВЕКМНОРСТУХ`) на латинские. Поля склеиваются через `\x1f`, иначе «Иванов Иван»
+ дата могут дать тот же вход, что и другое разбиение (тест
`test_canonical_string_separates_fields_unambiguously`).

### 2. Пользователь видит нормализованную форму до создания аккаунта

Регистрация в два шага: первый POST показывает `display_identity(...)` и просит
подтверждение, второй — создаёт. Между шагами **ничего не сохраняется**: значения
возвращаются через саму форму. Иначе пришлось бы положить ФИО в сессию, то есть
в БД, — ровно то, чего мы избегаем.

### 3. Одинаковый ответ и одинаковое время

Дубликат логина и дубликат личности дают одну и ту же страницу «заявка принята»
(тест сравнивает HTML), а вход для несуществующего логина выполняет Argon2id над
`dummy_hash()` — иначе по времени ответа можно перечислять аккаунты (T19).

### 4. Роль — колонка, а не имя логина

В схеме не было роли администратора: предполагалось, что «админ — это отдельный
аккаунт». При реализации это превратилось бы в проверку `login == "admin"` — то есть
в эскалацию привилегий через имя. Добавлена колонка
`app_user.role TEXT NOT NULL DEFAULT 'voter' CHECK (role IN ('voter','admin'))`;
`auth_level` в сессии выставляется из неё.

### 5. Сессии: в БД, хэш токена, ротация

Cookie `__Host-fv_sid` содержит 256-битный токен; в таблице `session` лежит
`SHA-256(token)`. Дамп БД не даёт валидных cookie, а украденная cookie отзывается
удалением строки. Ротация при входе (антификсация) и смена CSRF-токена при смене
уровня аутентификации. `session.created_at` — атрибут, а не ключ: иначе запись
`_created_at` через `__setitem__` помечала бы сессию изменённой на каждом запросе.

### 6. CSRF: почему выключен `WTF_CSRF_SSL_STRICT`

Flask-WTF в strict-режиме требует совпадающий `Referer`, а мы отдаём
`Referrer-Policy: no-referrer` — браузер его законно не пришлёт, и **все** формы
сломались бы в проде (тест это поймал). Вместо него работает независимый guard:
`Origin` / `Sec-Fetch-Site: same-origin`, плюс токен в серверной сессии. Это тот же
класс защиты без зависимости от заголовка, который мы сами запрещаем отправлять.

### 7. Rate limit: свой storage, потому что другого варианта нет

У `limits` нет SQLite-бэкенда, memory запрещён (несколько воркеров). `DBStorage`
реализует `incr/get/get_expiry/clear/reset/check` над таблицей `rate_counter` и
регистрируется в публичном реестре схем `limits` (`SCHEMES`). Ключ — `HMAC(k_ip_hash,
REMOTE_ADDR)`: открытый IP не хранится, TTL ≤ окна лимита.

### 8. Лимит считается по попыткам, а не по просмотрам

`GET /auth/login` и `POST /auth/login` — разные view: иначе каждый показ страницы
съедал бы бюджет «10 попыток за 15 минут» (поймано тестом: шестой GET получал 429).

### 9. Блокировка аккаунта

5 неудач → задержка 1, 2, 4, 8, 15 (максимум) минут; успешный вход сбрасывает
счётчик. Блокировка проверяется в сервисе, а не только лимитером по IP: распределённый
перебор по пулу адресов упрётся именно в неё.

## Что осталось (следующий инкремент, M2.3)

* TOTP: выдача секрета, подтверждение, анти-replay (`totp_last_step`).
* Recovery-коды: 10 штук, Argon2id, одноразовые, перегенерация.
* Пока TOTP не реализован, пользователь с включённым TOTP получает на входе `403`
  (fail-closed), а не «пускаем без второго фактора». Включить TOTP сейчас нельзя —
  эндпоинтов настройки нет, поэтому состояние недостижимо, но проверка уже стоит.

## Проверено

`223 passed`. Сценарии: регистрация в два шага, дубликат личности при другом логине,
PII в БД отсутствует (сканируются текстовые колонки), блокировка после 5 неудач,
429 на 11-й попытке входа, ротация cookie и CSRF-токена, истечение сессии, отзыв
сессий, чужой Origin → 403, отсутствие CSRF-токена → 400, открытый редирект отсечён.
