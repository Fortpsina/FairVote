# Runbook: развёртывание и эксплуатация FairVote

Документ для оператора. Правовой статус: платформа неофициальная и не имеет
юридической силы; перед реальными выборами нужна юридическая проверка (docs/04 A18).

---

## 1. Секреты (до первого запуска)

Нужны пять ключей по 32 байта в base64 и данные оператора:

| Переменная | Назначение | Обязательна |
|------------|-----------|-------------|
| `FV_SECRET_KEY` | подпись CSRF-токенов | да |
| `FV_MASTER_KEY` | HKDF → ключи шифрования TOTP | да |
| `FV_VOTER_PEPPER_V1` | соль `voter_key`; **ротация невозможна** | да |
| `FV_ED25519_SIGN_KEY` | подпись контрольных точек и выгрузок | да |
| `FV_BACKUP_KEY` | AES-256-GCM для бэкапа реестра | для бэкапов |
| `FV_OPERATOR`, `FV_LEGAL_BASIS`, `FV_CONTACT` | политика конфиденциальности | да в проде |
| `FV_DEMO_MODE` | `1` только для стенда | — |

Генерация:

```bash
python -c "import base64,os;print(base64.b64encode(os.urandom(32)).decode())"
```

Правила:

* секреты **не** попадают в git; `.gitignore` уже исключает `secrets.env`, `*.key`;
* на PythonAnywhere — файл `~/.fairvote/secrets.env` (`chmod 600`) вне web-root,
  читается в WSGI-файле;
* `FV_BACKUP_KEY` хранится **только офлайн**: иначе бэкап на том же хостинге
  бесполезен против этого хостинга;
* `FV_VOTER_PEPPER_V1` нельзя менять после первой регистрации: это сломает
  «один человек — один аккаунт» для всех существующих аккаунтов.

`python tools/vendor_libsodium.py --verify` должен проходить: он сверяет SHA-256
вендоренных скриптов с `fairvote/web/static/vendor/vendor.lock`.

## 2. Развёртывание на PythonAnywhere

1. Код в `/home/<user>/fairvote` (вне `/var/www`), виртуальное окружение, затем
   `pip install -r requirements.txt`.
2. WSGI-файл: прочитать `secrets.env`, выставить `FV_INSTANCE_DIR=/home/<user>/instance`,
   `from fairvote import create_app; application = create_app()`.
3. `instance/` вне web-root, `chmod 700`.
4. Static mapping `/static/` → `fairvote/web/static` (не через Flask: экономит CPU).
5. HTTPS принудительно; HSTS выдаётся приложением при `https`.
6. `flask init-db` — создаёт четыре схемы. **Миграций нет:** при изменении схемы
   нужен новый инстанс или ручной `ALTER TABLE`.
7. Scheduled task (раз в сутки): `flask daily`.

Проверка после деплоя:

```bash
flask show-db          # 8/7/4/2 таблицы
flask audit-head       # seq и голова цепочки
flask verify-chain     # проверка цепочки на сервере
curl -s https://<домен>/healthz
```

## 3. Ключевая церемония опроса

1. **Офлайн**, на машине, не подключённой к серверу: `python scripts/poll_keygen.py`
   → публичный и приватный ключ. Приватный ключ — на носитель/бумагу в сейф,
   по возможности разделить между N доверенными лицами (Shamir — не реализовано,
   см. docs/04 Q5).
2. Админ вставляет **публичный** ключ в `/admin/polls/<id>/key`; отпечаток
   попадает в публичный журнал (`poll.key_commit`).
3. Опубликуйте отпечаток в независимом канале (сайт кампании, соцсеть, зеркало):
   именно это, а не сервер, доказывает, что ключ не подменили.
4. После закрытия опубликуйте приватный ключ: `flask poll-publish-key` или через
   админку. Отпечаток сверяется с обязательством автоматически.
5. `flask poll-tally <id>` и `flask export-poll <id>` → артефакты для проверки.

Никогда не загружайте приватный ключ на сервер до закрытия: до этого момента
компрометация сервера не раскрывает голоса.

## 4. Ежедневная задача

`flask daily` выполняет:

| Шаг | Что делает |
|-----|-----------|
| `start_due` | открывает опросы, у которых наступило `starts_at` (снапшот допущенных) |
| `flush_batches` | сбрасывает накопленные бюллетени (порог 8 или 45 минут) |
| `close_due` | сбрасывает финальную пачку и закрывает истёкшие опросы |
| `export_public` | пишет подписанные `audit.jsonl`, `ballots-<poll>.jsonl`, `poll-<poll>.json` |
| `backup_registry` | шифрованный AES-256-GCM снапшот реестра (пропускается без `FV_BACKUP_KEY`) |
| `purge_retention` | обнуляет `voter_key` через `RETENTION_DAYS` после закрытия |
| `housekeeping` | сессии, счётчики лимитов, просроченные коды, брошенная очередь |
| `checkpoint` | подписывает голову цепочки (идемпотентно для неизменной головы) |

Запуск вручную и проверка отчёта:

```bash
flask daily            # JSON-отчёт: что открыто, закрыто, выгружено, почищено
flask verify-chain
flask audit-pubkey     # ключ, которым подписаны точки; опубликуйте его
```

После каждого запуска **опубликуйте голову цепочки** (`/transparency/head`) в
независимом канале. Без этого перезапись истории не будет обнаружена: подпись
сервера проверяется ключом сервера.

## 5. Бэкапы и восстановление

```bash
flask backup-registry                 # instance/backups/registry-<дата>.enc + .json
```

* `.enc` — AES-256-GCM, AAD привязан к дате; `.json` — метаданные и SHA-256.
* Скачивайте файлы с хостинга вручную: ключ офлайн, значит автоматическое
  восстановление «на том же сервере» бессмысленно.
* Восстановление: расшифровать ключом, проверить `sqlite3 <file> "PRAGMA integrity_check"`,
  положить на место `instance/db/registry.sqlite`, перезапустить web app.
* Публичные артефакты (`instance/exports/`) бэкапить не нужно: их можно
  пересоздать, а их ценность — в подписях и зеркалах.

Храните **два** независимых зеркала `audit.jsonl` и `ballots-*.jsonl`: газета,
репозиторий, чужой хостинг. Это единственная защита от переписывания журнала.

## 6. Закрытие и публикация результатов

```bash
flask poll-close <poll_id>
flask poll-publish-key <poll_id> --key-file /offline/poll-key.json
flask poll-tally <poll_id> --write
flask export-poll <poll_id> --out /tmp/verify-me
python scripts/verify.py --audit /tmp/verify-me/audit.jsonl \
  --ballots /tmp/verify-me/ballots.jsonl \
  --poll /tmp/verify-me/poll.json --poll-key /tmp/verify-me/key.json
```

Если `verify.py` вернул не `OK`:

1. Не публикуйте результаты.
2. Зафиксируйте вывод скрипта (коды расхождений: `BATCH_ROOT_MISMATCH`,
   `DISTRICT_MISMATCH`, `KEY_MISMATCH`, `TALLY_MISMATCH`…).
3. Опубликуйте инцидент вместе с головой журнала и кодом расхождения.
4. Помните: `verify.py` не чинит — он только показывает, где не сходится.

## 7. Удаление данных и retention

* `flask purge-retention` — то же, что в `daily`: обнуляет `voter_key` для людей,
  чьи опросы закрыты больше `RETENTION_DAYS` назад.
* Удаление аккаунта: `/account` → подтверждение паролем. Пока опрос не закрыт или
  не истёк срок хранения, удаление отклоняется — иначе можно было бы проголосовать
  дважды (docs/decisions/18).
* Просроченные заявки на верификацию закрываются в `daily` со статусом `rejected`
  и причиной `expired`.

## 8. Инциденты

| Событие | Что делать |
|---------|-----------|
| Утечка реестра (БД) | Считать `voter_key` скомпрометированным; уведомить пользователей; `FV_VOTER_PEPPER_V1` не меняется (сломает аккаунты), но `voter_key` можно обнулить досрочно через `purge-retention` |
| Утечка env (pepper + БД) | То же + считать возможной проверку членства по паспорту; уведомление обязательно |
| Потеря приватного ключа опроса | Результаты не публикуются, объявляется инцидент; `poll.close` остаётся в журнале |
| Расхождение головы журнала с зеркалом | Остановить публикацию результатов, зафиксировать обе головы, разбирать как перезапись истории |
| Скомпрометирован админ | Отозвать сессии (сменить пароль), проверить `admin_action` и журнал; правки после старта невозможны по конструкции |
| DDoS/накрутка | Лимиты в БД уже включены; при перегрузке — отключить регистрацию на уровне reverse proxy |

## 9. Что проверить перед реальным запуском

- [ ] юридическая проверка политики ПДн и согласия (политические взгляды — особая категория);
- [ ] публичный провайдер верификации выбран и работает (DemoProvider запрещён);
- [ ] `FD_BACKUP_KEY` существует офлайн, восстановление проверено;
- [ ] два независимых зеркала экспорта настроены;
- [ ] отпечаток ключа опроса опубликован до старта;
- [ ] `flask verify-chain` и `python scripts/verify.py` проходят на демо-данных;
- [ ] страница «Как это устроено» прочитана вслух: обещания совпадают с реализацией.
